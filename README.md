# Domivra

A platform for dormitory and condominium owners. It serves three roles:

- **Domivra platform admin** – manages customer accounts.
- **Property owner / manager** – manages their own data and residents.
- **Resident** – uses a mobile-friendly web app.

## Getting Started

Requirements: Node.js 22 or later, and Docker Desktop running.

```bash
cd domivra
npm ci
npm run setup
docker compose up --build -d
```

Open [Domivra](http://127.0.0.1:5173/login). The first-time platform admin credentials are stored inside the container:

```bash
docker compose exec -T api cat /app/runtime/platform-credentials.txt
```

If you have already changed the platform password and the file no longer matches the current one, reset it from the machine that manages Docker. This invalidates the existing platform admin sessions:

```bash
docker compose exec api node apps/api/dist/reset-platform.js
docker compose exec -T api cat /app/runtime/platform-credentials.txt
```

### Signing in

- **Platform admin:** use the organization code `platform`. From the platform page you can create customers, add owner accounts, issue new passwords, and suspend or reactivate organizations.
- **Property owners:** use the organization code generated by Domivra, then go to `/owner` to manage your residents.
- **Residents:** use `/app`, the resident web app.

Each organization's data is isolated by `org_id`, and the API checks role-based permissions on every request.

### Existing developer installs

Sample data from earlier developer installs has been migrated into an organization named `domivra`. This is a sample customer, **not** a platform admin account. Its `admin` and `resident` accounts use the original passwords stored in `data/initial-credentials.txt`.

A fresh clone starts with an empty database and a single platform account.

> **Never share the credentials file or `.env` with anyone.**

## Features

### By role

- **Platform:** create customer organizations and suspend or reactivate them.
- **Customer admins:** manage properties, rooms, residents, contracts, and bills; verify payment evidence; handle maintenance requests, common-area issue reports, announcements, house rules, and move-outs; view reports; and configure juristic-person, security, and emergency contact numbers.
- **Residents:** view bills and submit payment evidence; submit maintenance requests; report damaged common areas with live status updates; contact emergency services; read announcements and rules; view contracts; sign electronically; and request to move out.

### Contracts

- **Physical contracts:** use a scanned PDF and confirmation that the original copy has been received.
- **Electronic contracts:** confirmed by name, password, and consent, with a timestamp and the SHA-256 hash of the signed PDF.

### Room import

- Accepts `.csv` or `.xlsx` (first sheet only), up to 4 MB and 5,000 rows.
- Required headers: `property,building,number,floor,rent,deposit,area`.
- Optional headers: `room_type,water_meter,electric_meter,owner_name,owner_phone`.
- Duplicate rooms are skipped.
- This file is a room registry, **not** an import of resident identity data.

### Property data import

The "Property data" menu imports CSV or Excel files using the customer's own column headers (multiple sheets supported) and displays tables based on the imported columns.

- **Limits per file:** 4 MB, 20 sheets, 200 columns, 5,000 rows.
- **Storage:** rows are encrypted and isolated per organization.
- **Workflow:** after import, choose a dataset and map its columns to rooms, residents, contracts, or bills. Review the counts of new, duplicate, and error rows, then confirm to create the real records.
- **Results:** newly created resident accounts get individual passwords that can be downloaded once. Contracts await a document attachment and signature. Bills start as drafts.

### Resident registry

Owners manage the following from the Residents menu: nationality, contact channels, emergency contacts, co-residents, pets, vehicles, access cards, authorized persons, and move-in/move-out dates. They can also record room inspection results, visitors, and complaints. Lease and maintenance history are linked from existing records.

### Privacy

- Purposes and retention periods (in days) are configured per organization in Settings.
- Residents must confirm consent on the "My account" page before registry data is saved.
- ID card, passport, and visa numbers are encrypted in PostgreSQL. Document copies are stored in private S3.
- Owners see masked numbers by default and must explicitly reveal the full number; every reveal is written to an access log.

### Data retention

- Retention periods for the registry and personal documents start after the move-out process is closed.
- Standalone imported source datasets are deleted automatically after each property's `import_retention_days` (default: 365 days from import). Owners can delete them earlier.
- Deleting a source dataset does **not** delete the rooms, residents, contracts, or bills already created from it.

### Disclaimers

- Payment verification records the result of an admin checking the real bank account. The system does not transfer money.
- Electronic signing records confirmation evidence within the system, but it is **not** a digital signature from a certified provider.

## Configuration and Legacy Data

`npm run setup` generates random secrets in `.env` and creates `runtime/s3.json` without printing the values. Before updating an existing container, run it again to add `PII_ENCRYPTION_KEY` without changing existing secrets.

**Back up** `S3_SSE_KEK`, `PII_ENCRYPTION_KEY`, and the `storage_data` volume. If the keys are lost, encrypted documents and document numbers cannot be read. Do **not** run `docker compose down -v` while you still need the data.

The legacy SQLite data remains in `data/` and has not been deleted. The `npm run migrate:legacy` script imports the core data from the old database once, but it does not migrate evidence or contract files from the legacy system. In the sample data, one payment evidence record has no source file, so it was not imported into the new database. Keep `data/` as a reference copy.

The legacy `server.js` and `public/` are kept for reference. `docker compose` currently starts only the Vue web app, the API, and PostgreSQL.

## Production Readiness

Before using Domivra outside a development machine, prepare:

- HTTPS
- PostgreSQL and S3 backups
- Key management
- An identity verification and signing policy suitable for real-world use
